二、统一母样本：严格T0获额事件

步骤统一口径为什么需要
获额记录is_pass1=1、loan_type_code=2、recycle_type=3，取循环贷获额通过记录。限定为T0续贷场景。
20秒批次同一用户相邻获额记录不超过20秒时合并为一批；批内按获额时间倒序、订单编号倒序取第一笔。消除多产品或系统重复写入。
匹配结清单在同日、获额之前匹配实际放款且已结清订单；多笔候选取最近结清的一笔。明确本次T0由哪笔订单结清触发。
结清0在贷以该订单结清时点判断，用户不存在其他仍在贷订单。确保是真正的T0状态。
事件主键用户 × T0获额通过事件；同一用户可在不同时间产生多条事件。保留真实重复借款生命周期，不按用户月度去重。
提单归属一笔提单只归属其发生前最近一次T0事件；同一事件多笔提单只保留最早一笔。避免一个提单重复记到多次获额事件。

母事件伪代码

credit_events = 循环贷获额通过记录
credit_batches = 同一用户按时间排序，将相邻≤20秒记录合并
current_credit = 每批按 vir_time DESC, serial_id DESC 取第一笔

FOR each current_credit:
    candidates = 同用户、同日、在 vir_time 之前已结清的实际放款订单
    settled_order = candidates 按 repaid_time DESC, serial_id DESC 取第一笔
    REQUIRE 该时点不存在其他在贷订单
    OUTPUT user_id, vir_time, credit_serial_id, settled_serial_id
“上一笔订单”的固定定义：不是随便找一笔历史订单，而是触发当前T0事件的那笔“刚结清、实际放款”的订单。额度、使用率、息费、天数和借款次数都应以这个时点为基准。

四、基础指标字典

T0事件数
COUNT(*)，单位为用户 × T0事件。
T0用户数
COUNT(DISTINCT user_id)。仅在明确需要人数时使用，不与事件数混称。
提单事件数
指定观察窗口内存在首次提单的T0事件数。
提单率
提单事件数 / 合格T0事件数，必须带时间窗后缀。
放款事件数
指定窗口内首次提单对应订单最终成功放款的T0事件数。
放款率
成功放款事件数 / 合格T0事件数；若分母改为提单事件数，必须改名为“提单后放款率”。
事件占比
分组T0事件数 / 同月全部T0事件数。
用户占比
分组去重用户数 / 同月去重用户数。不能用事件占比代替。
平均提单时长
只在已提单事件中计算 AVG(apply_time-vir_time)。
月度归属
默认按T0获额通过日期 vir_date 归月；按到期日或放款月分析时必须另行标注。

  • 可按模型资质层比较时效和结构。

  • 下一笔使用率仅用于事后验证。

  • 缺失和-9999999不进入模型分分析。

六、额度变化、使用率与生命周期

6.1 额度变化

上一笔获额
触发T0的结清放款订单所对应的获额额度。
本次获额
20秒批次去重后当前T0获额通过订单的额度。
额度变化额
本次获额额度 − 上一笔获额额度。
额度变化率
本次获额额度 / 上一笔获额额度 − 1。
变化方向
差值>0为提额，=0为不变，<0为降额。
准确迁移路径
上一笔准确额度 → 本次准确额度，例如400→1320。
千元区间迁移
分别将两端额度映射到0—1000、1000—2000等区间，再形成区间路径。
分档版本管理：固定500/1000元档、千元区间档和结果驱动档是不同分析版本。不同报告采用不同分档时，只能比较原始方向与总体指标，不能直接比较单档结果。

6.2 上一笔与下一笔额度使用率

上一笔使用率
上一笔结清订单 remit_amt / 上一笔获额额度。用于圈人与解释，因为决策时已知。
下一笔使用率
下一笔放款金额 / 本次获额额度。仅用于事后验证，不能作为筛选条件。
汇总使用率
SUM(放款金额) / SUM(获额额度)，是金额加权比率，不是逐事件使用率的简单平均。
使用率档规则
<80%util < 0.8
80%—100%0.8 ≤ util < 0.999
接近100%0.999 ≤ util ≤ 1.001
>100%util > 1.001

6.3 借款次数

成功借款次数：在本次T0结清时点之前，成功放款且放款时间不晚于该结清时点的去重订单数。常用分档为1次、2次、3次、4次、5次、6次及以上。

生命周期含义：“借款2次用户”表示用户在本次T0事件发生时累计成功放款2次，不表示该用户最终一生只借2次。

在全分析样本上一次性计算P30和P60，并固定用于各月：≤P30为资质较差，P30—P60为资质一般，>P60为资质较好。不能每月重新计算阈值，否则月度结构无法比较。

8.2 资质较好内部三档

只在外层“资质较好”样本内计算P33和P67，再分为内部资质较差、内部资质一般、内部资质更好。该内部标签只描述“好客群内部的相对位置”，不能与外层资质较差混为一谈。

九、放款、逾期与到期盈利指标

9.1 成熟订单样本

  • 已放款：is_remit=1且remit_amt>0。
  • 整笔订单已到期：due_date < CURRENT_DATE-1；统计日当天到期订单不进入。
  • 按整笔订单到期日观察，不按分期到期日观察。

9.2 逾期率

未逾期订单
repaid_date > 2000-01-01且repaid_date ≤ due_date；到期日当天结清算未逾期。
逾期订单
结清日为空/无效，或repaid_date > due_date。到期后结清仍算逾期。
订单逾期率
逾期成熟订单数 / 成熟放款订单数。不使用loan_status_code=8判断。

9.3 到期盈利率

到期前回款
同订单还款流水中payin_date ≤ due_date的amount之和；到期后回款不计入。
到期利润
到期前回款 − remit_amt。
到期盈利率
SUM(到期前回款) / SUM(remit_amt) − 1，按金额加权。
成熟覆盖率
成熟放款订单数 / 全部放款订单数，用于判断近期月份结果是否稳定。
月份字段必须写清：可以按T0获额月看“获额队列后续质量”，也可以按到期月看“每天/每月到期订单质量”；两者回答的问题不同，不能共用同一个“月度盈利率”名称。

十、提单率变化归因

设某客群1月、8月的结构占比分别为 w0、w1，提单率分别为 r0、r1，1月整体提单率为 R0。

基准档内效应
w0 × (r1-r0)：保持1月结构不变，只看客群提单率变化。
纯结构效应
(w1-w0) × (r0-R0)：客群占比变化相对1月整体水平造成的影响。
交互效应
(w1-w0) × (r1-r0)：结构和客群提单率同时变化产生的共同项。
结果档内效应
w1 × (r1-r0)，等于基准档内效应＋交互效应。
总归因贡献
结果档内效应＋纯结构效应。各互斥客群贡献求和等于整体提单率变化。
如何读：负值表示该客群在统计分解中拉低整体提单率，正值表示抵消部分下降。贡献大需要同时具备足够规模、明显的档内变化或显著的结构变化。
不能推导：归因贡献不是策略因果效应。提额客群贡献了多数下降，只能说明“提额客群的提单率下降值得重点解释和提升”，不能证明“提额导致提单率下降”。

当前指标多产品规则含义

十二、圈人、预测模型与实验指标

12.1 特征时间原则

信息是否可用于筛选/模型特征说明

最近2—3次获额、提单、额度使用历史可以比简单历史均值更能反映近期状态。
获额后页面行为视触达时点只能用于行为发生之后的实时触达，不能用于获额时点模型。
下一笔使用率、下一笔逾期和盈利不可以未来结果，只能作标签或事后验证。

12.2 运营实验

目标客群
风险可控、历史盈利较好、额度/产品条件存在不满足、当前尚未提单的用户。
短期可执行动作
提供较低息费的优惠；产品多选需要产品部门配合，适合作为中期方案。
实验转化率
实验组观察窗内提单人数或事件数 / 实验组触达数，与随机对照组同口径比较。
增量提单率
实验组提单率 − 对照组提单率。
增量利润
增量放款带来的到期利润减去优惠成本、坏账增量和触达成本。

十三、跨报告比较与统一命名规范

容易混淆的项目统一要求不能混用的原因
用户数 vs 事件数标题、表头必须标“用户”或“T0事件”。一个用户可多次进入T0，事件数通常更大。
D0 vs 24h vs D7提单率名称必须带时间窗。自然日、滚动小时和8个自然日的覆盖范围不同。
事件占比 vs 用户占比分子、分母都按同一粒度。高频复借用户会放大事件占比。
上一笔使用率 vs 下一笔使用率前者用于筛选，后者只做验证。下一笔属于未来信息。
平均事件比率 vs 金额加权比率额度使用率、盈利率默认用金额加权，若用简单平均需另行标注。大额订单与小额订单权重不同。
获额月 vs 放款月 vs 到期月月度图标题中明确队列月份字段。同一订单在三个口径下可能属于不同月份。
确认埋点 vs 真实提单前者叫确认触达率，后者以订单表为准。点击确认不一定生成有效订单。
归因贡献 vs 因果效果归因只作统计分解；策略效果需随机实验或严谨因果方法。结构和用户选择偏差可能同时存在。
外层资质档 vs 好客群内部三档内部标签必须带“外层好客群内部”。内部“较差”仍属于外层资质较好。
完整月 vs 截止日部分月份在标题和数据标签加截止日或“*”。规模、成熟度和行为覆盖不完整。

推荐字段命名

t0_event_cnt                 -- T0事件数

apply_d0_event_cnt           -- 当天提单事件数

apply_24h_event_cnt          -- 滚动24小时首次提单事件数
apply_24h_rate               -- 获额后24小时首次提单率
apply_d7_event_cnt           -- T0至D+7首次提单事件数
apply_d7_rate                -- T0至D+7提单率
credit_change_amt            -- 额度变化额

推荐建模方式：建立一张稳定的T0事件宽表，以事件主键存放所有“当时已知”的基础特征；D0、D7行为和后续订单质量分别做派生事实表。这样既能复用同一母样本，又能防止未来信息泄漏。
