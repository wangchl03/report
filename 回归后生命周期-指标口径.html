回归后生命周期——指标口径文档

SQL 分析 首次流失 >7天 后又回归用户

一、数据范围

分析对象首次流失（>7天间隔）后又回归的用户
生命周期用户回归后至少有一笔放款，且最终状态非在途、非刚结清的回归用户
生命周期用户数41,021 人
平均生命周期75.2 天

二、生命周期定义

┌────────────────────────── 回归后生命周期 = 75.2 天 ──────────────────────────┐ │ │ ▼ ▼ 回归首笔提单日 最后一笔放款的到期日/结清日 (first_return_apply_date) (MIN(repaid_date, due_date))
端点来源含义
起点first_return_apply_date触发流失判定间隔的那笔"下一笔提单"的申请日期
终点MIN(repaid_date, due_date)最后一笔放款取结清日和到期日中的较小值
终点 (status=8)due_date逾期未结清时，取还款计划的到期日

三、在途天数 52.3 天

定义

有放款订单（is_remit = 1）活跃的天数。

公式（事件流法）

订单活跃区间 = [apply_date, 结束日] ↑ 含头 ↑ 含尾 status = 7 (已结清) : 结束日 = repaid_date status = 8 (逾期未还): 结束日 = due_date

图示

放款订单 │ │ apply_date ◄────────── 在途 ──────────► repaid_date / due_date │ │ │ │ ├─────────────── 在途天数 ──────────────┤ │ │ apply日和repaid日都算在内 │ │ │ │ ▼ ▼ ▼ ──┼──────╔════════════════════════════╗──────────┼── ║ 在途 (有活跃贷款) ║ ╚════════════════════════════╝

并发在途订单

订单A: apply──╔═══════════╗──repaid ║ ║ 订单B: apply──╔════╬══════╗──repaid ║ ║ ║ ║ ╚══════╩════╩══════╝ 双重在途 ↑ 单笔在途 并发

事件流法自动处理并发：有 N 笔订单活跃就算在途，全结清才停止。并发不重复计数天数。

四、被拒天数 6.3 天

定义

提单被拒（is_remit = 0）到下一次成功放款（is_remit = 1）之间的等待天数。排除该期间有在途订单的时段。

公式

被拒天数 = 下次放款.apply_date - 本次被拒.apply_date ↑ 含头（被拒日算入） ↑ 不含尾（下次放款日不算入）

图示

被拒申请 下次放款（成功） │ │ ▼ ▼ ──┼──╔══════════════════════╗─────┼── ║ 被拒天数(等待审核) ║ ╚══════════════════════╝ ▲ ▲ 含头 不含尾

被拒期间有在途订单时

被拒申请 在途订单(还清中) 下次放款 │ ╔═══╗ │ ▼ ║ ║ ▼ ──┼──────────────╔╬═══╬╗──────────────┼── ║║ ║║ ╚╩═══╩╝ 在途(不算被拒)

优先级：在途 > 被拒。被拒 gap 中如果存在活跃的放款订单，整段不计入被拒。

连续多笔被拒

被拒A──被拒B──被拒C────────下次放款 │ │ └──── 只取最早一笔A ───────┘ B和C已包含在A的gap中

按下次放款分组，每组只取最早被拒申请，避免重叠计数。

五、无在途天数 15.5 天

定义

一笔放款结清后、到下次提单前，没有任何在途订单、也不在被拒期间的空白天数。

公式

无在途 = 下次提单.apply_date - 本次结清.repaid_date - 1 ↑ 不含 ↑ 不含

图示

排除条件

条件说明
gap_days <= 0偿还日和下次申请日重叠或负间隔
has_other_active = 1gap 期间有其他放款订单活跃
