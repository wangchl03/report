指标口径文档

用户生命周期定义与经营拆解口径

以首贷成功放款用户为对象，按当前状态确定生命周期终点，并将生命周期拆解为逾期、在途、被拒与无在途四段。

目录

  1. 统计对象与分析范围
  2. 生命周期定义、五类用户与伪代码
  3. 四段生命周期的边界、优先级与伪代码
  4. 计算生命周期的目的与经营含义

一、统计对象与分析范围

项目口径
源表订单表；订单、放款、结清、到期及当前订单状态均从订单表取得。
统计用户首贷提单日期在 2024-01-01 至 2026-06-30（含）之间，且首贷订单成功放款的用户。
用户粒度按 user_id 去重；只要用户存在一笔满足范围的首贷成功放款订单，即进入样本。
不纳入用户只有提单、但首贷未成功放款的用户，不进入生命周期统计样本。
生命周期起点用户的首贷提单日期 first_loan_apply_date，而非首贷放款日。
本口径以“首贷成功放款用户”为分析起点；后续生命周期状态则基于该用户截至统计时点的全部订单表现进行判断。

二、生命周期定义与五类当前状态

生命周期从首贷提单日开始，到用户当前状态对应的终点日结束，按自然日含首尾计算。

生命周期总天数 = 生命周期终点 - 首贷提单日期 + 1

2.1 五类用户分类与生命周期终点

状态用户分类口径生命周期终点
逾期状态当前存在至少一笔整笔订单状态为 8。所有当前逾期订单中，最早的 due_date。
被拒状态不存在状态为 8 的订单，且最后一笔提单订单未成功放款。最后一笔被拒订单的 apply_date。
在途状态不存在状态为 8 的订单、最后一笔提单不是被拒，且存在至少一笔状态为 5 的订单。所有在途订单中，最晚的 due_date。
流失状态不存在逾期、被拒、在途；最后一笔订单已结清，结清后未再提单，且最后结清日距统计日大于 7 天。最后一笔已结清订单的 repaid_date。
正常结清状态订单均已结清，且不属于逾期、被拒、在途或流失；最后结清日距统计日小于等于 7 天。最后一笔已结清订单的 repaid_date。
状态判定按表中顺序依次执行，以保证互斥。例如同时有在途与逾期订单时，归为逾期状态；最后一笔被拒而仍有旧在途订单时，归为被拒状态。

2.2 五类用户分类伪代码

FOR EACH user_id: first_loan_apply_date = 首贷成功放款订单的首贷提单日期 last_apply_order = 按 apply_time、serial_id 倒序的最后一笔提单 last_settled_order = 最后一笔有效结清订单 IF EXISTS(当前订单状态 = 8): user_status = '逾期状态' lifecycle_end = MIN(当前状态8订单.due_date) ELSE IF last_apply_order 未成功放款: user_status = '被拒状态' lifecycle_end = last_apply_order.apply_date ELSE IF EXISTS(当前订单状态 = 5): user_status = '在途状态' lifecycle_end = MAX(当前状态5订单.due_date) ELSE IF last_settled_order.repaid_date 距统计日 > 7 天 AND last_settled_order 结清后无新的提单: user_status = '流失状态' lifecycle_end = last_settled_order.repaid_date ELSE: user_status = '正常结清状态' lifecycle_end = last_settled_order.repaid_date

三、生命周期四段拆解

在每位用户的 [首贷提单日，生命周期终点] 内，对每一个自然日赋予唯一状态。四段天数之和必须严格等于生命周期总天数。

生命周期总天数 = 逾期天数 + 被拒天数 + 在途天数 + 无在途天数
日状态优先级：逾期 > 在途 > 被拒 > 无在途。优先级用于处理同日提单、结清、放款等交叠情形。
逾期天数

历史逾期后已结清订单：overdue_days > 0 且当前订单状态不为 8。

开始：due_date + 1 天

结束：repaid_date，结清日计入逾期。

在途天数

至少有一笔成功放款订单处于正常借款期，且当天不属于逾期。

开始：成功放款订单的 apply_date。

结束：MIN(repaid_date, due_date)；提单日与到期日均计入。

被拒天数

非逾期、非在途期间，结清后发生被拒提单所形成的整段等待链路。

开始：被拒提单之前最近一笔成功订单的结清次日。

结束：下一笔成功放款订单 apply_date - 1 天；若无下次成功放款，取生命周期终点。

无在途天数

仅指订单结清后、下一次提单直接成功放款前的可提单空档；只要下一次提单被拒，整段均不属于无在途。

开始：已结清订单 repaid_date + 1 天。

结束：下一次直接成功放款提单 apply_date - 1 天；期间还须无逾期、无在途、无被拒。

3.2 关键同日规则

情形当天归属原因
逾期订单结清当日，又发生被拒或成功放款逾期结清日仍属于该笔逾期区间，逾期优先级最高。
先被拒、同日又成功放款在途成功放款提单日属于在途；被拒区间在成功放款当日前结束。
多笔在途订单并发在途只计 1 天按用户—日期去重，不能将并发订单天数相加。
多笔逾期区间交叠或连续逾期只计 1 天先合并逾期区间，再按用户—日期计算。

3.3 四段计算伪代码

FOR EACH user_id: calendar_days = 首贷提单日 至 lifecycle_end 的全部自然日 overdue_intervals = 合并所有历史逾期已结清订单的区间 [due_date + 1 天, repaid_date] in_transit_intervals = 合并所有成功放款订单的区间 [apply_date, MIN(valid_repaid_date, due_date)] rejected_intervals = 对每笔被拒订单： [被拒前最近成功订单的 repaid_date + 1 天, 下一笔成功放款 apply_date - 1 天] 若不存在下一笔成功放款，则结束日 = lifecycle_end idle_intervals = 对每笔已结清订单： 仅当下一次提单直接成功放款时： [repaid_date + 1 天, 下一次成功放款提单 apply_date - 1 天] 仅保留无逾期、无在途且不在被拒等待期的日期 FOR day IN calendar_days: IF day IN overdue_intervals: day_status = '逾期' ELSE IF day IN in_transit_intervals: day_status = '在途' ELSE IF day IN rejected_intervals: day_status = '被拒' ELSE IF day IN idle_intervals: day_status = '无在途' lifecycle_days = COUNT(calendar_days) overdue_days = COUNT(day_status = '逾期') in_transit_days= COUNT(day_status = '在途') rejected_days = COUNT(day_status = '被拒') idle_days = COUNT(day_status = '无在途') ASSERT lifecycle_days = overdue_days + in_transit_days + rejected_days + idle_days

四、为什么要计算生命周期

本课题的目的不是只计算用户“存活多久”，而是识别生命周期中哪些时间可通过经营转化为新的借款机会与未来盈利。

时间段经营解释主要动作方向
逾期用户暂不具备正常提单资格，生命周期损失主要来自风险与未结清。催收、还款修复、风险策略，不把它误认为转化不足。
被拒用户表达了需求，但没有形成放款。核查拒绝原因、授信额度、审批策略与产品匹配。
在途用户已成功借款，正在承接收入与潜在利润。保障履约体验、控制风险，并为后续回归创造条件。
无在途用户具备提单资格却没有形成新的借款。这是重点经营空间：触达、产品匹配、额度与定价优化。
核心经营指标：无在途天数占比 = 无在途天数 / 生命周期总天数。在风险、让利和审批质量可控的前提下，降低该占比、提升可提单用户转化为成功放款的比例，才能增加用户生命周期内的放款与盈利机会。

需要注意：将无在途时间转化为在途时间，代表增加放款机会，而不等于自动增加最终净利润；仍需同时观察通过率、逾期、让利成本和单笔利润。
