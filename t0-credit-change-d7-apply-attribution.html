提额>1200还能继续集中到三个互斥叶子

结论 05

降额异常可继续集中到相对降幅较小、借款次数较少的三个叶子

降额≤1000是绝对贡献最大的降额金额父群；继续叠加降额比例和成功借款次数后，三个互斥叶子合计9,169次事件，占全部T0事件5.05%，却解释整体下降8.33%。其中“降额比例≤8%＋借款≤4次”提单率由79.70%降至65.31%，归因浓度最高。

结论 06

原始差异含明显客群结构影响，必须保留因果边界

8月原始提单率为：降额68.33%、不变75.73%、提额63.66%。在相同月份、上一笔额度带、借款次数和上一笔使用率的共同样本中，标准化后分别为71.42%、75.43%、75.49%。原始差异大幅收窄，说明客群和策略结构是重要混杂因素。

二、统计口径与分析边界

事件与额度口径

  • 样本：上一笔已结清且结清时0在贷，随后T0获额通过。
  • 单位：用户 × T0事件，同一用户多次T0分别统计。
  • 20秒去重：相邻获额≤20秒为一批，按获额时间倒序、订单编号倒序取第一笔。
  • 额度变化 = 当前T0获额 − 刚结清订单对应的上一笔获额。

T0至D+7提单口径

  • apply_time ≥ vir_time，且 apply_time < vir_date + 8 days，覆盖T0、D+1……D+7，共8个自然日。
  • 同一T0事件窗口内多笔提单只计首次；若同一用户窗口内出现新的T0事件，提单归给发生前最近一次T0，避免重复归因。
  • 统计期：2026-01-01至2026-09-20；9月是部分月，规模不可与整月直接比较。
  • 第一层是观察性归因；标准化减少可观测结构差异，不等价于因果识别。

    END AS change_amount_bucket,

      WHEN e.credit_change_rate <= -0.50 THEN '降幅50%及以上'

        FROM bucketed
        GROUP BY t0_month, target_bucket

        SELECT t0_month, SUM(n) AS total_n,
          SUM(apply_n)/NULLIF(SUM(n),0) AS overall_rate
        FROM monthly GROUP BY t0_month
      ), weighted AS (
        SELECT m.*, m.n/t.total_n AS weight, t.overall_rate
        FROM monthly m JOIN total t USING (t0_month)
      ), jan AS (
        SELECT * FROM weighted WHERE t0_month=DATE '2026-01-01'
      ), paired AS (
        SELECT c.t0_month, c.target_bucket,
          j.n AS jan_n, c.n AS current_n,
          j.weight AS jan_weight, c.weight AS current_weight,
          j.rate AS jan_rate, c.rate AS current_rate,
          j.overall_rate AS jan_overall_rate
        FROM weighted c JOIN jan j USING(target_bucket)
      )
      SELECT TO_CHAR(t0_month,'YYYY-MM') AS t0_month, target_bucket,
        jan_n, current_n,
        ROUND(100*jan_weight,2) AS jan_share_pct,

        ROUND(100*jan_rate,2) AS jan_rate_pct,
        ROUND(100*current_rate,2) AS current_rate_pct,

        ROUND(100*(current_weight-jan_weight)*(jan_rate-jan_overall_rate),2)
          AS structure_effect_pp,

          +(current_weight-jan_weight)*(jan_rate-jan_overall_rate)

        FROM bucketed
        GROUP BY target_bucket, credit_change_type
      ), period_direction AS (
        SELECT credit_change_type, SUM(event_n) AS direction_event_n
        FROM period GROUP BY credit_change_type
      ), period_total AS (
        SELECT SUM(event_n) AS all_event_n FROM period

        FROM tmp_t0_credit_change_d7_apply
        WHERE credit_change_type IN ('额度增加', '额度降低')
      ), grouped AS (
        SELECT credit_change_type, previous_band_lower, current_band_lower,
          COUNT(*)::numeric AS event_n,
          COUNT(DISTINCT user_id)::numeric AS user_n,
          SUM(has_d7_apply)::numeric AS d7_apply_n,
          SUM(CASE WHEN t0_month = DATE '2026-01-01' THEN 1 ELSE 0 END)::numeric
            AS jan_event_n,

                   THEN has_d7_apply ELSE 0 END)::numeric AS jan_apply_n,
          SUM(CASE WHEN t0_month = DATE '2026-08-01' THEN 1 ELSE 0 END)::numeric
            AS aug_event_n,
          SUM(CASE WHEN t0_month = DATE '2026-08-01'
                   THEN has_d7_apply ELSE 0 END)::numeric AS aug_apply_n
        FROM banded
        GROUP BY credit_change_type, previous_band_lower, current_band_lower
      )

          PARTITION BY credit_change_type

        ROUND(100.0 * jan_apply_n / NULLIF(jan_event_n, 0), 2) AS jan_rate_pct,
